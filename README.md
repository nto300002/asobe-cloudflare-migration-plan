## 1. 目的と基本方針

2027年2月1日からのSites課金変更を契機に、業務アプリのホスティング・永続データをCloudflareへ移行する。5サイト合計の月額予算は5米ドル以下、目標は0米ドル。各アプリで独立したGoogle認証を採用し、既存業務・UI・データの継続性を優先する。移行完了目標は2027年1月24日、最終期限は1月31日とする。課金開始日・適用条件は前回計画とユーザー提示を前提とし、契約上の最新条件は切替前に再確認する。

## 3. アプリとログインの分離方針

2026年11月27日の決定により、在庫管理、プリントオーダー、プリントマニュアル、封入・納品管理、KIIYA見落としチェッカーの**5アプリを統合しない**。asobeの4アプリも、それぞれ独立したアプリとして移行する。共通ポータル、共通ログイン、共通セッション、アプリ別パスを持つ統合Workerは作らない。

各アプリに別のWorker、別URL、別Google OAuthクライアントとリダイレクトURI、別セッションCookie、別の権限設定、別D1、必要な場合は別R2バケット、別GitHubリポジトリ、別デプロイ手順を設ける。同じGoogleアカウントを各アプリで使う場合でも、ログイン状態とアクセス許可は共有しない。あるアプリからログアウトしても他のアプリのセッションを変更しない。相互のデータ参照は行わない。

Cloudflareアカウントを共有するかは所有権と費用を踏まえて決める。同一アカウントを使う場合でも、アプリごとのデプロイトークンは他アプリの資源を変更できない権限にする。KIIYAの組織所有権が異なる場合はCloudflareアカウント自体も分離する。

本番データの全件照合、画像原本の復元試験、利用人数は未確認。ソースの GitHub 登録と5サイトへの初期実装は実施したが、Cloudflare への移行は実施していない。

### 全件ダウンロード機能の確定仕様

**目的と範囲:** 管理者が各サイトの管理画面から、既存の業務レコードを1件も省かずに取得し、同じ時点のテーブル一覧と構造を確認できるようにする。画面上の検索・日付・表示件数による絞り込みは全件ダウンロードに適用しない。対象はエクスポート作成時の配備先 D1 を調べ、GitHub のスキーマだけを正本としない。CSV は閲覧用の補助形式であり、復元用の原本は型と null を保つ JSON Lines または SQL とする。

**管理画面の操作:** 「業務データ全件とテーブル構造をダウンロード」を押すと、対象 DB、含まれる業務テーブルと件数見込み、画像の有無、秘密情報の扱いを表示する。管理者が開始するとジョブ ID と状態（準備中・完成・失敗）を表示し、完成後だけ「ダウンロード」を有効にする。生成中の再操作は既存ジョブを案内し、失敗時は不完全なファイルをダウンロードさせない。プリントマニュアルでは既存のパスキーによる追加確認をダウンロードにも適用する。その他のサイトもサーバー側でその時点の管理者権限を再検査し、権限不足は 403、未ログインは 401 とする。開始とダウンロードの両方を監査ログに記録する。

**出力物:** サイトごとに次の構成の ZIP を作る。ファイル名にはサイト名と UTC の生成時刻を含め、ZIP 内は UTF-8 とする。複数のアーカイブに分割した場合も共通のエクスポート ID を付ける。

```text
<site>-<UTC timestamp>.zip
  manifest.json
  schema/schema.sql
  schema/tables.json
  data/<table>.jsonl
  assets/manifest.json             # 画像を持つサイトのみ
  assets/objects/00000001.bin       # 画像を持つサイトのみ。安全な連番名
<site>-<UTC timestamp>.sha256        # ZIP 外の照合用ファイル
```

| ファイル | 必須内容 |
| --- | --- |
| `schema/schema.sql` | 配備中 D1 から取得したテーブル、ビュー、インデックス、トリガーの `CREATE` 定義。順序と依存関係を保ち、復元に不要な内部オブジェクトの扱いを明記 |
| `schema/tables.json` | **全ユーザーテーブル**の名前、列名、型、NULL 可否、既定値、主キー順、生成列、外部キー、ユニーク制約、インデックス、トリガー、固定時点の件数。値を出さない技術・認証テーブルも一覧と構造には含め、値の除外理由を記録 |
| `data/<table>.jsonl` | 対象業務テーブルの**全行**。1行1レコードで列名と元の値を保持し、ID・日時・削除状態・外部キーを変換しない。BLOB があれば base64 と型を明記。0件のテーブルにも空ファイルを作る |
| `assets/manifest.json` | R2 とソース埋込写真の対象一覧。各原本について元のバケット・オブジェクトキー（ソース埋込写真は元の識別子）、参照元レコード、ZIP 内の生成パス、MIME、サイズ、SHA-256 を一対一で記録する。ファイルが欠けた場合は完了扱いにしない |
| `manifest.json` | エクスポート ID、サイト URL、生成日時、ソース版、DB 識別子、スキーマと許可リストの版・ハッシュ、各テーブルの分類・固定時点の件数・出力件数・除外理由、**自身を除く** ZIP 内の各ファイルのサイズと SHA-256、画像件数、書込み停止・再開時刻、整合性検査結果、完全／失敗の状態。分割時は全パートの番号とファイル名を記録する。秘密値は記録しない |
| `<site>-<UTC timestamp>.sha256` | ZIP の外に置く照合用ファイル。単一 ZIP または全分割 ZIP のファイル名・サイズ・SHA-256 を記録し、完成した ZIP から最後に生成する。自身のハッシュは記録しない |

`manifest.json` 自身のサイズと SHA-256 は `manifest.json` に含めない。ZIP 全体を検証する場合は外部の `.sha256` ファイルを照合し、分割時は全パートが揃い、各パートのハッシュが一致してから ZIP 内のマニフェストと原本を検証する。

**ZIP 内のパス:** R2 のキーやソースファイル名を ZIP エントリー名へ直接連結しない。画像にはエクスポート内で一意の連番名 `assets/objects/<8桁の番号>.bin` を生成し、元のキーとの対応は `assets/manifest.json` のみに保存する。全エントリーは固定の相対パスに限定し、絶対パス、`..`、バックスラッシュ、シンボリックリンク、重複パスを作成時と復元時の両方で拒否する。分割 ZIP では各パートに同じエクスポート ID とパート番号を付け、全パートの検証が終わるまで復元を開始しない。

テーブル定義は D1 の `sqlite_schema` と対応する `PRAGMA table_xinfo`、`foreign_key_list`、`index_list`、`index_xinfo` 等で照合する。D1 がサポートする SQL と `PRAGMA` の範囲は[公式 SQL 文書](https://developers.cloudflare.com/d1/sql-api/sql-statements/)に従い、実装時に各配備 DB で確認する。運用者による別経路の検証・復元用には、[Wrangler の `d1 export --remote`](https://developers.cloudflare.com/d1/best-practices/import-export-data/)でスキーマとデータの SQL ダンプを取得できる。管理画面に Cloudflare API トークンを渡したり、Public GitHub に出力物を保存したりしない。

**サイト別の業務データ候補:** 在庫管理は `items`、`daily_inventory`、`shortage_requests`。プリントオーダーは `app_state` の版番号と JSON 全体を原本とし、その中の注文・制作実績等を CSV に展開できるようにする。プリントマニュアルは `users`、`manual_documents`、`manual_videos`、`manual_video_preview_checks`、`progress`、`progress_archives` と写真原本。封入・納品管理は `variants`、`balances`、`deliveries`、`delivery_lines`。KIIYA は `app_users`、`works`、`work_changes`、`images`、`report_versions`、マスタ変更履歴、報告配送履歴と画像原本。これらは公開ソースから得た候補であり、配備 DB の実体と照合してから許可リストへ登録する。

**テーブル・列の許可リスト:** 各アプリに版管理した出力ポリシーを置き、業務データとして値を出すテーブル名と列名を明示する。配備 DB の全ユーザーテーブル・全列・ビュー・トリガーを列挙してポリシーと比較し、未分類のテーブル、新しい列、想定外の構造変更が一つでもあれば、そのエクスポートは**失敗として停止**する。新規テーブルを名前や命名規則だけで業務データへ自動追加しない。所有者が用途・機密性・参照関係を確認し、`業務データ出力`、`構造と件数のみ`、`別管理の暗号化バックアップ対象`を明示的に分類してポリシーを更新した後に再実行する。確認中に作った部分ファイルはダウンロードさせない。未分類の名前と停止理由は監査ログに残すが、値は記録しない。

**JSON列の許可リスト:** `app_state.data` を含む JSON 格納列は、列名だけでなく JSON の全階層のキー・型・配列要素の形を版管理した出力ポリシーで検査する。任意の追加キーや未検査の JSON オブジェクトを許す設定は使わない。ID をキーとする辞書など可変キーが必要な箇所は、許されるキーの形式と値の構造を明示し、その内側も再帰的に検査する。エクスポート前に各行の JSON を重複キーも検出できる方法で解析し、未知のキー、重複キー、型違い、解析不能な値が一つでもあれば、**元の JSON 全体の出力を停止**してポリシーの確認を求める。プリントオーダーの `app_state` はこの検査に合格した版だけを、版番号と検証済み JSON を保って出力する。ポリシーの版・ハッシュと検査結果を `manifest.json` に残し、JSON 内部を検査しない生データ経路を設けない。

**機密テーブル:** セッション、パスキー、認証チャレンジ、OAuth トークン、Chatwork 認証設定などの値は通常の業務ダウンロードに入れない。ただし、そのテーブルの名前・列・制約・件数と除外理由は `schema/tables.json` と `manifest.json` に必ず残す。認証状態を含めた完全な DB 復旧が必要な場合は、管理画面の通常ダウンロードとは別に、運用者が全 DB の SQL ダンプを取得し、暗号化して保管する。業務上必要な職員・利用者の対応関係は、秘密値を除いた移行用の表として定義し、管理者だけが取得する。

**一貫した取得時点:** 各アプリでエクスポート開始前にサーバー側の書込み停止を有効にし、通常の書込みAPI、管理API、画像アップロード、定期処理、キュー、外部連携からの書込みをすべて拒否または待機させる。進行中の書込みが完了したことを確認した時刻を固定時点とし、停止中に配備先 D1 の構造・全対象行と R2 のオブジェクト一覧・原本を取得する。ジョブ状態と監査記録は対象 D1/R2 の固定時点を変えない別の管理ストアに記録するか、固定の前後に記録する。D1 と R2 の取得・ハッシュ検査が完了するまで停止を維持し、完了または失敗を記録してから書込みを再開する。書込み経路を一つでも停止できない場合は全件エクスポートを開始しない。D1 のスナップショット等を代替手段として採用する場合も、R2 を含む同一時点の固定方法と全書込み経路の扱いを実装・検証してから切り替える。**件数や版の前後比較だけを一貫性の根拠にしない。**

**30分を超える画像取得:** 事前に D1 の容量、R2 の全オブジェクト数・総容量、実測転送速度を確認する。30分以内の段階取得を使えるのは、対象オブジェクトの**原本バイト列からアップロード時に計算した SHA-256**とサイズを元キーに結び付けて永続保存し、R2 への書込み権限を監査可能な保存経路に限定して同じキーの上書きを禁止し、削除も記録できる場合に限る。サイズ・更新日時・ETag だけを原本のハッシュとして代用しない。先行コピーでは書込みを続けたまま原本を非公開・変更不可の一時領域へ複製し、コピー側で計算した SHA-256 を保存済み原本ハッシュと照合する。停止後は進行中の処理の完了を待ち、D1 の構造・対象行と R2 の全キー一覧を固定し、元キーと保存済みハッシュ・サイズに対応する検証済みコピーを選ぶ。先行コピー後に追加されたキーは停止中に新しい生成名で複製・ハッシュ照合し、削除済みキーは対象から外す。**全原本を停止中に再読込することを30分以内の計画に含めない。** 保存済みハッシュがない既存画像、上書きや管理外の変更を否定できない画像、ハッシュ不一致の画像が一つでもあれば、その画像だけを先行コピーで確定したとみなさず、下記の保守時間に切り替えて対象全体を取得する。D1・R2 の同一固定時点の検証済みコピーが30分以内に揃った場合だけ書込みを再開し、ZIP 化・分割・配布は停止解除後に行う。30分以内に揃わなければ成果物を失敗扱いにして書込みを再開する。保守時間では、運用者が実測容量と転送速度から終了期限を設定して事前に告知し、その時間中は全書込みを停止したまま D1 と R2 の全原本を読み、SHA-256 を計算して一時領域へ取得する。生存通知・監視・手動解除を適用し、期限に達した場合は失敗として解除して、容量に見合う保守時間を再設定して最初から取得する。いずれの方法でも、固定時点の原本が一つでも欠ける、またはハッシュが異なる場合は完成としない。

**停止ジョブの異常終了と解除:** 書込み停止は永続的なフラグではなく、ジョブ ID・世代番号・有効期限を持つ排他的なリースで管理する。リースの有効期限は2分、生存通知は30秒以内ごと、管理画面から開始する1回の停止の最長時間は30分とする。30分を超える見込みの場合は上記の段階取得と保守時間の手順を適用する。全書込み経路は同じ権威あるリース状態を確認し、状態が読めない場合は勝手に書込みを再開しない。生存通知が途絶えたら監視処理または次の書込み要求が期限切れを検出し、ジョブを失敗扱いにして書込みを再開する。期限切れや解除後の旧ジョブは世代番号で遮断し、生成途中のファイルを完成として公開できない。管理者による手動解除は、対象ジョブの状態を確認して強制中止し、部分ファイルを無効化し、解除理由・操作者・時刻・世代番号を別の監査記録に残してから行う。管理ストアの障害で通常の解除ができない場合は、運用者が同じ中止・外部監査記録・再開確認を行う非常手順を用意する。解除後は書込みAPIと定期処理が再開したことを確認し、失敗したエクスポートは最初から作り直す。

**整合性検査:** 固定時点の各テーブルの `COUNT(*)` と出力行数、全ファイルの SHA-256、外部キー参照、画像件数・ハッシュを照合する。件数一致だけでは値の一致を保証しないため、出力ファイルのハッシュと復元後の列値照合を必須とする。画像が大きいマニュアルと KIIYA は非公開の一時保管と分割ダウンロードを使い、期限切れ後に一時ファイルを消す。実装前に配備版ソース、D1・R2 の実体と容量、書込み経路を確認する。

**復元試験を2種類に分ける:** (1) 管理画面の業務エクスポートは、空の検証 DB に `schema.sql` の構造と許可リスト対象の行だけを復元し、対象テーブルの件数・ID・日時・列値・参照関係、画像原本のハッシュを照合する。構造のみ出力した機密・技術テーブルの復元先件数は元 DB と一致しないことを前提とし、それを不合格にしない。必要な参照先が除外テーブルにある場合は、移行用の非秘密対応表または隔離した検証用レコードで参照関係を確認する。(2) 別管理の暗号化した完全 DB バックアップは、外部連携を無効にした隔離環境に全テーブル・全行を復元し、**機密・技術テーブルも含めて**件数と構造を照合する。業務エクスポートの合格を完全 DB の復元成功とみなさず、それぞれ独立した証跡と合否を記録する。

**受け入れケース:** 管理者が業務データ全件と全テーブルの構造を取得し、許可リスト対象の行数・列値・ハッシュが一致すること。0件のテーブルも構造と、対象なら空ファイルがあること。未分類テーブル・列、または既知の JSON 列内に未知のキーを追加した検証環境では出力が停止し、秘密値が含まれないこと。閲覧・編集権限の利用者と未ログイン利用者は API を直接呼んでも取得できないこと。書込み停止中の書込みAPI・定期処理・R2アップロードが拒否または待機されること。ジョブを強制終了して生存通知を止めた場合と管理者が手動解除した場合に、期限内に書込みが再開し、旧ジョブの部分ファイルが公開されないこと。`../`、絶対パス、バックスラッシュ、同名に正規化される文字列を含む R2 キーでも ZIP 内の生成パスが安全で一意になり、元キーへ復元できること。保存済み SHA-256 と不変性を確認できる原本では30分以内の段階取得を完了し、保存済みハッシュがない既存画像や管理外の変更がある場合は期限付き保守時間へ切り替えて全原本を取得すること。先行コピー後に追加・削除されたオブジェクトの取りこぼし、分割パートの欠損・ハッシュ不一致、停止期限超過があれば成功と表示されず書込みが再開すること。`manifest.json` は自身のハッシュを含まず、外部の `.sha256` で単一 ZIP または全分割 ZIP のハッシュを照合できること。R2 の欠損、期限切れダウンロードは成功と表示されないこと。業務エクスポートと完全 DB バックアップを別々に復元し、上記の異なる合格条件を満たすこと。各ケースについて操作・HTTP 応答・マニフェスト照合結果を証跡として残す。

## 5. 移行先アーキテクチャ

| 項目 | 5アプリ共通の分離ルール |
| --- | --- |
| ホスティング・URL | アプリごとに独立Workerと独立URL。パスで統合しない |
| 静的配信 | 各アプリのWorkerに付属する Workers Static Assets で HTML・CSS・JavaScript 等を配信。API・SSRは当該Workerで処理 |
| 認証 | アプリごとに独立したGoogle OIDCクライアント、コールバック、セッションCookie、許可ユーザー管理 |
| DB | アプリごとに独立D1。認証用テーブルも原則そのアプリのD1内に置き、他アプリと共有しない |
| 画像 | 必要なアプリに専用R2バケット。画像原本を他アプリと共有しない |
| Git | 上記のサイト別GitHubリポジトリを維持し、ソースを一つのアプリへ統合しない |
| デプロイ | アプリごとに独立CI／Wrangler設定と最小権限トークン |

D1はまず各アプリ1 DB、計5 DBを設計上の出発点とする。実際のDB数と無料枠は契約時に再確認し、検証環境のDBも含めて費用を計算する。共通認証DBと共通ポータルは設けない。

### Sites の技術要件と静的配信

**配信方式:** 5つの業務アプリでは各Workerに[Workers Static Assets](https://developers.cloudflare.com/workers/static-assets/)を付属させる。ビルド成果物の公開用ディレクトリをアプリごとのWrangler設定の`assets.directory`に指定し、HTML・CSS・JavaScript・公開可能な画像を配信する。API、OAuthコールバック、サーバー描画が必要な画面は同じアプリのWorkerで処理する。Cloudflare PagesはAPIを持たない独立した案内サイト等の選択肢とし、この5アプリの標準構成には採用しない。R2の業務画像原本や報告ファイルはStatic Assetsへ配置しない。

| Sitesでの現行構成・依存 | Cloudflare移行時の要件 |
| --- | --- |
| 5サイトの公開ソースはNext.js/ReactとSitesのWorkerビルドを使用 | アプリごとに実際のビルド成果物とSSR・API経路を確認し、Cloudflare Workersで動くビルド設定へ移す。Node.jsサーバー専用APIやSites固有ランタイムへの依存は個別に置換・検証する |
| `.openai/hosting.json` にD1の`DB`、必要な2サイトにR2の`BUCKET`を宣言 | 各アプリ専用のWrangler設定・環境別bindingに置き換え、本番と検証環境のDB・バケットを取り違えない。デプロイ前にbinding名と実体を照合する |
| Sitesのサインインと`oai-authenticated-user-id`等の認証ヘッダー | 前節のアプリ別Google OIDCとセッションへ置き換え、既存ユーザーID・所有者・役割を承認済み対応表で移行する。ヘッダーをCloudflare本番でも受け取れる前提にしない |
| Sitesの実行時環境変数・秘密値 | 公開ソースや静的成果物から除外し、各Workerの秘密設定へ移す。プレビューと本番の値・権限を分ける |
| Sitesの版と静的成果物 | 各アプリのGitコミット、Workerコード、静的成果物、DBマイグレーションを対応付けて配備・ロールバックする。配備中にHTMLとアセットが異なる版から返る可能性を踏まえ、旧画面が参照するファイルの読み込みも検証する |

**認証を通す経路:** Static Assetsは既定で一致するファイルをWorkerより先に返す。公開可能なアセットと、認証が必要なHTML・ファイルの経路をアプリごとに列挙する。保護対象は[`assets.run_worker_first`](https://developers.cloudflare.com/workers/static-assets/routing/worker-script/)の対象としてWorkerで認証・認可してから返す。SPAのフォールバックやSSR経路も、未ログイン利用者が保護画面・データを取得できないことを確認する。フロントエンドの表示制御だけに依存せず、APIとR2配信でも権限を検査する。

**費用と受入条件:** Workerを実行せず静的ファイルが返る要求は無料だが、Workerを先に実行する経路・API・SSRはWorkersの利用量に入る。[公式の課金条件](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/)に従い、静的要求と動的要求を別に計測する。各アプリで未ログイン・一般職員・管理者の画面/API/R2アクセス、静的ファイルの配信、更新直後の旧画面、失敗時のロールバックを検証し、URL・HTTP応答・ビルド版を証跡に残す。

### 技術選定

プリントオーダーは既存Vinext構成を優先。Sites専用の認証ヘッダー、.openai/hosting.json、ビルド・環境変数依存を調査し、Cloudflare本番用設定とD1/R2 bindingを整備する。pnpm lockfileを尊重し、Node.js 22.13以上でビルド検証する。その他は回収コードに合わせ、必要な場合のみReact/TypeScript/Vite/Hono/Drizzleを採用する。各アプリを独立して移行し、全面書き換えやソースの統合は行わない。

### Google認証・権限

各アプリでAuthorization Code Flow + PKCE、state、nonce、署名・iss・aud・exp検証を行う。アプリごとにGoogle subを永続識別子とし、そのアプリの既存SitesユーザーIDとは管理者承認の対応表で紐付ける。許可済みユーザーのみアクセス可能とし、管理者・職員・作業担当者の権限は各アプリのAPI側で検査する。CookieはSecure/HttpOnly/SameSite、CSRF対策、退職時のセッション失効を実装。Cookieの名前と適用範囲、ログアウト先をアプリごとに分ける。R2は非公開とし当該アプリの認証済みAPIで配信する。

### KIIYA固有の検証

既存設計にChatwork連携、毎分監視・遅延照合・日次処理の候補がある。現行サイトの実装有無を確認し、必要ならWorkers Cron等で再現性・重複送信防止・実行時間・費用を検証する。外部Cloud Tasks等は費用未確定のため採用保留。

## 6. 費用計画・上限制御

Workers Freeを基本とし、有料化は承認制とする。以下は前回計画で参照した公式仕様に基づく設計値で、契約時点に再確認する。同一アカウント内の全アプリで枠を共有する。

| 項目 | 無料枠（設計値） | 警戒ライン |
| --- | --- | --- |
| Workers | 10万動的要求/日、CPU 10ms/要求 | 7万要求/日 |
| 静的配信 | Workerを呼ばないStatic Assets要求は無料・無制限。`run_worker_first`対象はWorkers要求として計測 | 静的処理と動的処理を区別 |
| D1読込 | 500万行/日 | 350万行/日 |
| D1書込 | 10万行/日 | 7万行/日 |
| D1容量 | 合計5GB、個別500MB、10 DB | 個別350MB |
| R2 Standard | 10GB-month、Class A 100万/月、B 1000万/月 | 7GB、操作枠70% |

試算：15人×50操作/日×3 API = 2,250要求/日、各API100行読込なら225,000行/日、操作あたり2行書込なら1,500行/日。画像2GBと仮定すれば上記主要枠内。ただし認証・定期処理・バックアップ・CPUは別途実測する。

R2は無料枠超過で従量課金される。保存量・アップロードサイズ・操作回数をアプリ側で制御し、上限接近時は管理者通知と不要な書込み停止を行う。予算通知は強制課金停止を保証しない。Workers Paidは基本5ドル/月に超過料金・税が加わる可能性があるため、総額5ドルの厳守には不向き。独自ドメインは購入しない前提。

### 運用と所有権

本番アカウントは事業所の管理権限を確保する。GitHubとCloudflareの最小権限を設定し、KIIYAのデプロイトークンはasobeの資源を変更できないようにする。組織が別でアカウントも分離する場合、費用は両アカウントの合計で管理する。

## 7. データ・ソースコード回収

優先順：①現行ソースとエクスポートの取得、②管理者限定のエクスポート機能追加、③取得不可の場合は画面・仕様から再実装。現行本番への変更はバックアップと承認の後に限る。

| 回収対象 | 確認・保全内容 |
| --- | --- |
| コード | フロント、API、依存・lockfile、設定、テスト、スキーマ |
| DB | 全レコード、ID、日時、外部キー、件数、容量、削除状態 |
| ファイル | 写真原本、MIME、サイズ、SHA-256、参照先 |
| 認証 | 既存ID、権限、所有者対応表（秘密値除外） |
| 仕様 | 全画面、操作、エラー、外部連携、スクリーンショット |

## 9. 切替・復旧・未決事項

### 本番切替

初回移行 → 試験運用 → 旧サイト更新停止 → 最終差分取得・取込 → 件数・内容・画像照合 → 新URL周知 → 新環境での業務開始 → 旧Sites停止・課金状態確認。切替失敗時は新環境の更新分を退避・照合して旧環境へ復帰する。旧環境のデータ削除は復元可能性と管理者承認を確認した後に限る。

### バックアップ

D1は毎日SQLエクスポート、R2は毎週・変更時に原本バックアップ、コード・スキーマは変更ごとにGit管理。暗号化した外部ストレージに週次保管し、月1回空の検証DBへ復元する。D1 Time Travel（無料7日、有料30日）は補助として利用する。

例：npx wrangler d1 export inventory-db --remote --output=./backups/inventory.sql

例：npx wrangler d1 execute inventory-restore-test --remote --file=./backups/inventory.sql
